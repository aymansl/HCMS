## 5. Architecture constraints

- Modular Monolith with ASP.NET Core MVC (.NET 10), EF Core + SQL Server, Identity with permission-based policies, SignalR notifications, QuestPDF reports, Razor + Bootstrap, Arabic RTL UI.
- Separate AI service (Python FastAPI) called over REST with header `X-API-Key`; the system must keep working when it is down (HTTP 503 → continue without the AI feature).
- Every order/case (lab request, imaging request/session, emergency case) is a **state machine**: allowed transitions only, and each transition stores a timestamp + user (turnaround time, S4).
- Data modelled with HL7 FHIR in mind (ServiceRequest / Observation / DiagnosticReport / Encounter naming where reasonable).

### UC-L01 — Log In / Log Out (تسجيل الدخول والخروج) · requirement L1 · increment 2

- **Actors:** فني المخبر
- **Preconditions:** يجب أن يكون لفني المخبر حساب مسجل في النظام بدور «فني مخبر».
- **Postconditions:** يحصل فني المخبر على صلاحية الوصول إلى لوحة المخبر، أو يُنهى جلسته عند تسجيل الخروج.
- **Main flow:**
  1. يطلب فني المخبر تسجيل الدخول.
  2. يعرض النظام نموذج تسجيل الدخول.
  3. يدخل فني المخبر البريد الإلكتروني وكلمة المرور.
  4. يتحقق النظام من صحة البيانات ومن دور المستخدم.
  5. يمنح النظام فني المخبر الوصول إلى لوحة المخبر.
  6. عند انتهاء العمل يختار «تسجيل الخروج» فيُنهي النظام الجلسة ويعيده إلى صفحة الدخول.
- **Alternative flow:** إذا كانت بيانات الدخول غير صحيحة:
  - يعرض النظام رسالة «البريد الإلكتروني أو كلمة المرور غير صحيحة».
  - يبقى نموذج الدخول مفتوحاً للمحاولة مرة أخرى.
- **Exceptions:**
  - حساب فني المخبر موقوف: يرفض النظام الدخول ويعرض رسالة بذلك.
  - خمس محاولات دخول فاشلة متتالية: يُقفل الحساب مؤقتاً.

| Test | Scenario | Input | Expected result |
|---|---|---|---|
| TC-L1-01 | تسجيل دخول ببيانات صحيحة | بريد وكلمة مرور صحيحان لحساب فني مخبر فعّال | يفتح النظام لوحة المخبر |
| TC-L1-02 | كلمة مرور خاطئة | بريد صحيح وكلمة مرور خاطئة | رسالة «البريد الإلكتروني أو كلمة المرور غير صحيحة» ويبقى النموذج مفتوحاً |
| TC-L1-03 | قفل الحساب | خمس محاولات فاشلة متتالية ثم محاولة صحيحة | يرفض النظام الدخول ويعرض أن الحساب مقفل |
| TC-L1-04 | تسجيل الخروج | الضغط على «تسجيل الخروج» ثم محاولة فتح لوحة المخبر | تنتهي الجلسة ويُعاد المستخدم إلى صفحة الدخول |

### UC-L02 — View Incoming Requests (عرض الطلبات الواردة إلى المخبر) · requirement L2 · increment 2

- **Actors:** فني المخبر
- **Preconditions:** فني المخبر مسجّل الدخول.
- **Postconditions:** تُعرض الطلبات الواردة مرتبة حسب وقت الوصول مع حالة كل طلب.
- **Main flow:**
  1. يفتح فني المخبر صفحة «الطلبات الواردة».
  2. يجلب النظام الطلبات بالحالات: مطلوب، مستلَم، قيد التنفيذ.
  3. يعرض النظام الطلبات مرتبة حسب وقت الوصول مع اسم المريض والطبيب والتحاليل والحالة.
  4. يختار فني المخبر طلباً لعرض تفاصيله.
- **Alternative flow:** إذا اختار فني المخبر التصفية:
  - يحدد الحالة أو التاريخ أو اسم المريض.
  - يعرض النظام الطلبات المطابقة فقط.
- **Exceptions:**
  - لا توجد طلبات واردة: يعرض النظام رسالة «لا توجد طلبات حالياً».

| Test | Scenario | Input | Expected result |
|---|---|---|---|
| TC-L2-01 | عرض الطلبات | وجود 3 طلبات بحالات مختلفة | تظهر الطلبات الثلاثة مرتبة حسب وقت الوصول |
| TC-L2-02 | التصفية حسب الحالة | اختيار الحالة «مطلوب» | تظهر الطلبات ذات الحالة «مطلوب» فقط |
| TC-L2-03 | لا توجد طلبات | قاعدة بيانات بلا طلبات واردة | رسالة «لا توجد طلبات حالياً» |

### UC-L03 — Receive Lab Test Request from Doctor (استقبال طلب التحليل من الطبيب) · requirement L3 · increment 2

- **Actors:** فني المخبر، الطبيب
- **Preconditions:** أنشأ الطبيب طلب تحليل من ملف المريض.
- **Postconditions:** تصبح حالة الطلب «مستلَم» ويُسجَّل وقت الاستلام.
- **Main flow:**
  1. يرسل الطبيب طلب التحليل من ملف المريض.
  2. يُشعر النظام المخبر لحظياً بوصول طلب جديد.
  3. يفتح فني المخبر الطلب.
  4. يتحقق فني المخبر من بيانات المريض والتحاليل المطلوبة.
  5. يؤكد فني المخبر الاستلام، فيحفظ النظام الحالة «مستلَم» ووقت الاستلام.
- **Alternative flow:** إذا كان الطلب ناقصاً:
  - يختار فني المخبر «إعادة إلى الطبيب» ويكتب ملاحظة.
  - يعيد النظام الطلب إلى الطبيب مع الملاحظة.
- **Exceptions:**
  - سجل المريض غير موجود: يرفض النظام الطلب ويُنبّه الطبيب.

| Test | Scenario | Input | Expected result |
|---|---|---|---|
| TC-L3-01 | استلام طلب صحيح | طلب تحليل لمريض موجود | يظهر الطلب لحظياً في المخبر، وبعد التأكيد تصبح حالته «مستلَم» مع وقت الاستلام |
| TC-L3-02 | طلب لمريض غير موجود | معرّف مريض غير موجود | يُرفض الطلب ويُنبَّه الطبيب |
| TC-L3-03 | طلب ناقص | طلب بلا تحاليل محددة، ثم «إعادة إلى الطبيب» مع ملاحظة | يعود الطلب إلى الطبيب مع الملاحظة |

### UC-L04 — Receive Test Request Cancellation (استقبال إلغاء طلب التحليل من الطبيب) · requirement L4 · increment 2

- **Actors:** فني المخبر، الطبيب
- **Preconditions:** يوجد طلب تحليل لم تصدر نتيجته بعد.
- **Postconditions:** تصبح حالة الطلب «ملغى» ويُسجَّل وقت الإلغاء وسببه، ولا يمكن إدخال نتيجة له.
- **Main flow:**
  1. يلغي الطبيب طلب التحليل ويكتب السبب.
  2. يتحقق النظام من أن النتيجة لم تصدر بعد.
  3. يغيّر النظام حالة الطلب إلى «ملغى» ويسجل الوقت والسبب.
  4. يُشعر النظام المخبر لحظياً بالإلغاء.
  5. يطّلع فني المخبر على الإلغاء فيُوقف العمل على العينة.
- **Alternative flow:** إذا كانت العينة قد سُحبت:
  - يسجل فني المخبر ملاحظة «عينة مسحوبة – أُلغي الطلب».
  - يحفظ النظام الملاحظة في سجل الطلب.
- **Exceptions:**
  - النتيجة صدرت مسبقاً: يرفض النظام الإلغاء ويُعلم الطبيب بأن النتيجة صادرة.

| Test | Scenario | Input | Expected result |
|---|---|---|---|
| TC-L4-01 | إلغاء طلب قبل صدور النتيجة | طلب بحالة «مستلَم» ثم إلغاء من الطبيب | تصبح الحالة «ملغى» ويصل إشعار للمخبر |
| TC-L4-02 | إلغاء بعد صدور النتيجة | طلب بحالة «صادرة» ثم محاولة إلغاء | يرفض النظام الإلغاء ويُعلم الطبيب |
| TC-L4-03 | منع إدخال نتيجة لطلب ملغى | محاولة إدخال نتيجة لطلب «ملغى» | يمنع النظام الإدخال |

### UC-L05 — Receive Appointment Booking from Patient (استقبال حجز موعد من المريض) · requirement L5 · increment 2

- **Actors:** فني المخبر، المريض
- **Preconditions:** المريض مسجل الدخول، ولديه طلب تحليل يحتاج إلى سحب عينة.
- **Postconditions:** يُحجز موعد سحب العينة ويُشعر المخبر والمريض.
- **Main flow:**
  1. يختار المريض «حجز موعد مخبر» من بوابته.
  2. يعرض النظام الأوقات المتاحة في المخبر.
  3. يختار المريض وقتاً مناسباً.
  4. يتحقق النظام من توفر الوقت ويحفظ الحجز.
  5. يُشعر النظام فني المخبر بالحجز الجديد ويرسل تأكيداً للمريض.
  6. يظهر الحجز في جدول المخبر اليومي.
- **Alternative flow:** إذا أراد المريض تغيير الموعد:
  - يختار المريض الحجز ثم «تعديل».
  - يختار وقتاً آخر متاحاً فيحدّث النظام الحجز ويُشعر المخبر.
- **Exceptions:**
  - الوقت المختار حُجز للتو من مريض آخر: يرفض النظام الحجز ويطلب اختيار وقت آخر.

| Test | Scenario | Input | Expected result |

| TC-L5-01 | حجز وقت متاح | اختيار وقت فارغ | يُحفظ الحجز ويصل إشعار للمخبر وتأكيد للمريض |
| TC-L5-02 | حجز وقت محجوز | حجزان متزامنان للوقت نفسه | يُقبل الأول ويُرفض الثاني مع طلب اختيار وقت آخر |
| TC-L5-03 | تعديل الحجز | تغيير الوقت إلى وقت متاح | يتحدث الحجز في جدول المخبر |

### UC-L06 — Manage Tests (إدارة التحاليل (إضافة، تعديل، حذف)) · requirement L6 · increment 2

- **Actors:** فني المخبر
- **Preconditions:** فني المخبر مسجّل الدخول ولديه صلاحية إدارة كتالوج التحاليل.
- **Postconditions:** يُحدَّث كتالوج التحاليل (الاسم، والوحدة، والقيم المرجعية، والسعر).
- **Main flow:**
  1. يفتح فني المخبر صفحة «كتالوج التحاليل».
  2. يختار «إضافة تحليل».
  3. يدخل الاسم والوحدة والقيم المرجعية الدنيا والعليا والسعر.
  4. يتحقق النظام من صحة البيانات وعدم تكرار الاسم.

  2. يبحث النظام في ملفات المرضى وحالات الإسعاف.
  3. يعرض النظام النتائج مع وجود حالة مفتوحة أو عدمه.
  4. يختار المشرف المريض فيعرض النظام بياناته الأساسية.
- **Alternative flow:** إذا لم يوجد المريض:
  - يعرض النظام «لا يوجد ملف» مع خيار «تسجيل حالة جديدة» (UC-E02).
- **Exceptions:**
  - للمريض حالة إسعاف مفتوحة: ينبّه النظام المشرف ويعرض الحالة بدل فتح حالة جديدة.

### UC-E02 — Register Emergency Case and Assign Doctor (تسجيل حالة إسعاف وتعيين طبيب لها) · requirement E2 · increment 6

  5. يحفظ النظام الحالة ويُشعر الطبيب لحظياً.
- **Alternative flow:** للمريض ملف سابق:
  - تُربط الحالة بملف المريض بدل إنشاء ملف جديد.
- **Exceptions:**
  - لا يوجد طبيب متاح: توضع الحالة في الانتظار ويُنبَّه المدير.

### UC-E04 — Record and View Preliminary Patient Info (تسجيل البيانات الأولية للمريض وعرضها) · requirement E4 · increment 6

- **Actors:** مشرف قسم الإسعاف
- **Preconditions:** توجد حالة إسعاف مفتوحة.
- **Postconditions:** تُحفظ الأعراض والفحص الأولي والحالة الصحية والعنوان في الحالة، وتظهر للطبيب المعيَّن.
- **Main flow:**
  1. يفتح المشرف حالة الإسعاف.
  2. يدخل الأعراض ونتائج الفحص الأولي (الضغط، النبض، الحرارة، التشبع) والحالة الصحية والعنوان.
  3. يتحقق النظام من صحة القيم.
  4. يحفظ النظام البيانات مع الوقت.
  5. تظهر البيانات للطبيب المعيَّن في ملف الحالة.
- **Alternative flow:** تعديل البيانات لاحقاً:
  - يحدّث المشرف القيم فيحفظ النظام نسخة جديدة مع وقت التعديل في سجل التدقيق.
- **Exceptions:**
  - قيم غير منطقية (نبض سالب مثلاً): يعرض النظام رسالة خطأ.
  - الحالة مغلقة: يمنع النظام التعديل.

| TC-E4-02 | قيمة غير منطقية | نبض = -5 | رسالة خطأ |
| TC-E4-03 | حالة مغلقة | تعديل حالة مغلقة | يمنع النظام التعديل |

### UC-E06 — Issue Daily Emergency Report (إصدار التقرير اليومي للإسعاف) · requirement E6 · increment 6

- **Preconditions:** مشرف الإسعاف مسجّل الدخول.
